# Feature Specification: UI 框架采纳与前端重构

**Feature Branch**: `005-ui-framework-adoption`
**Created**: 2026-05-06
**Status**: Draft
**Input**: User description: "目前前端存在很多交互和展示问题，我认为用一个现成的 UI框架更好，根据目前的风格，业务目标，挑选一个合适的"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 框架基础替换与视觉一致性 (Priority: P1)

作为用户，我希望应用的视觉风格在引入 UI 框架后保持液体玻璃的半透明、模糊、高光边框等核心视觉特征不变，同时获得更专业、更一致的交互反馈（按钮状态、焦点环、过渡动画等）。

**Why this priority**: 如果框架引入破坏了现有的液体玻璃视觉身份，整个迁移就没有意义。视觉一致性是所有后续工作的基础。

**Independent Test**: 在暗色主题下打开应用，所有面板仍然呈现半透明渐变背景、背景模糊、高光边框和深度阴影；交互元素（按钮、输入框、复选框）有清晰的 hover/focus/active 状态；现有的焦点环样式完整保留。

**Acceptance Scenarios**:

1. **Given** 应用使用新的 UI 框架渲染，**When** 用户查看任意面板区域，**Then** 面板仍然具有 `backdrop-filter: blur`、半透明渐变背景、高光边框和深度阴影
2. **Given** 应用使用新的 UI 框架渲染，**When** 用户通过键盘 Tab 导航，**Then** 每个交互元素都有可见的焦点环
3. **Given** 应用使用新的 UI 框架渲染，**When** 用户将鼠标悬停在按钮或控件上，**Then** 有清晰的视觉反馈（颜色变化或亮度变化）
4. **Given** 应用使用新的 UI 框架渲染，**When** 用户的系统设置了减少动画偏好，**Then** 所有过渡和动画被禁用

---

### User Story 2 - 改进的导入与队列交互 (Priority: P1)

作为用户，我希望导入媒体文件时有更流畅的交互体验：文件选择器更直观、上传进度清晰可见、每个文件的导入状态（排队/上传中/已接受/重复/不支持/失败）用明确的视觉指示区分，而不是依赖纯文本标签。

**Why this priority**: 导入是媒体库的核心入口流程，当前的手写 CSS 实现在状态区分、进度展示和错误反馈方面表现粗糙，直接影响用户对产品可靠性的感知。

**Independent Test**: 导入混合类型的文件集，验证每个文件状态有独立的视觉标识（图标+颜色+文字）、进度条平滑更新、失败项有明确的错误描述和可操作的指导。

**Acceptance Scenarios**:

1. **Given** 用户点击导入按钮，**When** 文件选择器打开，**Then** 选择器支持多文件选择并显示可接受的媒体类型
2. **Given** 文件正在上传，**When** 上传进行中，**Then** 每个文件显示平滑更新的进度指示
3. **Given** 文件导入完成，**When** 文件状态为已接受/重复/不支持/失败，**Then** 每种状态用不同的图标和颜色清晰区分
4. **Given** 导入队列中有失败项，**When** 用户查看失败项，**Then** 失败项显示具体的错误原因和可操作的建议

---

### User Story 3 - 改进的筛选与浏览交互 (Priority: P2)

作为用户，我希望筛选控件更加直观和紧凑：下拉菜单代替平铺的选项、标签选择器支持搜索、日期范围选择更易用、活跃筛选条件一目了然且容易移除。

**Why this priority**: 当前 9 个筛选维度全部平铺在侧边栏，占用大量空间且交互原始。改善筛选体验直接提升日常浏览效率。

**Independent Test**: 在有大量资产和标签的库中，使用各筛选控件缩小范围，验证下拉选择、标签搜索、日期选择和组合筛选都能正确工作，且活跃筛选条件能一键清除。

**Acceptance Scenarios**:

1. **Given** 侧边栏显示筛选控件，**When** 用户展开筛选下拉菜单，**Then** 选项以可滚动列表呈现，支持搜索过滤
2. **Given** 用户已选择标签筛选，**When** 标签数量较多，**Then** 标签选择器支持搜索缩小范围
3. **Given** 用户设置了日期范围，**When** 用户打开日期选择器，**Then** 可以方便地选择起止日期
4. **Given** 用户已应用多个筛选条件，**When** 用户查看活跃筛选区域，**Then** 所有活跃条件以芯片形式显示，每个芯片可单独移除，也可一键全部清除

---

### User Story 4 - 改进的批量操作与确认 (Priority: P2)

作为用户，我希望批量操作有专业的交互流程：选择资产后出现浮动工具栏、批量操作有加载和结果反馈、删除操作有明确的确认对话框（显示影响数量）而非浏览器原生 `confirm()`。

**Why this priority**: 批量操作是高频功能，当前的实现缺乏中间状态反馈，删除确认使用浏览器原生弹窗，体验粗糙。

**Independent Test**: 选择 10 个以上资产，执行批量打标签、批量收藏和批量删除，验证浮动工具栏跟随选择状态出现、操作有进度反馈、删除弹出专业确认对话框。

**Acceptance Scenarios**:

1. **Given** 用户选择了多个资产，**When** 选择数量大于 1，**Then** 底部出现浮动工具栏显示选择数量和可用操作
2. **Given** 用户触发批量操作，**When** 操作执行中，**Then** 显示加载指示器，按钮禁用防止重复提交
3. **Given** 批量操作完成，**When** 有部分失败，**Then** 结果反馈区分成功和失败数量，失败项可查看原因
4. **Given** 用户点击批量删除，**When** 确认对话框弹出，**Then** 对话框显示将删除的资产数量，需明确确认才执行

---

### User Story 5 - 改进的资产详情面板 (Priority: P2)

作为用户，我希望资产详情面板更像一个精心设计的信息展示区域：元数据分组清晰、标签编辑更方便（输入即搜索已有标签）、收藏切换有动画反馈、面板在移动端以抽屉形式滑入。

**Why this priority**: 详情面板是用户深入了解单个资产的主要界面，当前的信息展示比较原始，缺少分组和视觉层次。

**Independent Test**: 点击任意资产卡片，验证详情面板展示分组元数据、标签可编辑且支持搜索、收藏按钮有切换动画、在窄屏下以侧滑抽屉展示。

**Acceptance Scenarios**:

1. **Given** 用户打开资产详情，**When** 面板渲染完成，**Then** 元数据按类别分组（文件信息/相机信息/视频信息），每组有标题
2. **Given** 用户编辑标签，**When** 用户在标签输入框中输入文字，**Then** 下拉显示匹配的已有标签供选择
3. **Given** 用户切换收藏状态，**When** 点击收藏按钮，**Then** 按钮有平滑的状态切换动画
4. **Given** 用户在窄屏设备上，**When** 点击资产卡片，**Then** 详情以从右侧滑入的抽屉形式展示，可滑动关闭

---

### User Story 6 - 响应式布局与健康面板优化 (Priority: P3)

作为用户，我希望在不同屏幕尺寸下应用都能良好展示：大屏三栏布局、中屏双栏、小屏单栏带抽屉导航。健康状态面板以更紧凑的卡片和进度条展示，而不是纯文本列表。

**Why this priority**: 响应式和健康面板是体验优化的增量改进，不影响核心功能使用但提升专业感。

**Independent Test**: 在不同视口宽度下验证布局切换；在存在健康问题的库中验证问题以卡片形式展示且有严重程度指示。

**Acceptance Scenarios**:

1. **Given** 用户在大屏设备上，**When** 视口宽度超过 1050px，**Then** 应用展示三栏布局（侧边栏 + 内容 + 详情）
2. **Given** 用户在移动设备上，**When** 视口宽度小于 680px，**Then** 应用切换为单栏布局，侧边栏和详情面板以抽屉形式展示
3. **Given** 库中存在健康问题，**When** 用户打开健康面板，**Then** 问题以紧凑卡片展示，每张卡片标明严重程度、影响数量和建议操作

---

### Edge Cases

- 当标签数量为零时，标签筛选器应显示空状态提示而非空白
- 当导入全部失败时，摘要区域应突出显示失败原因而非仅显示计数
- 当筛选结果为空时，内容区应显示有意义的空状态（而非空白网格）
- 当批量操作中途网络断开时，已完成的部分应保留，失败的部分应标记为可重试
- 当详情面板打开时切换筛选条件，面板应保持打开或根据筛选结果更新

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 应用 MUST 采用基于无头原语的可定制 UI 组件框架，确保视觉风格可以完全自定义而不与框架默认样式冲突
- **FR-002**: 应用 MUST 保留液体玻璃视觉风格，包括半透明渐变背景、背景模糊、高光边框和深度阴影
- **FR-003**: 应用 MUST 使用统一的主题令牌系统（颜色、圆角、间距），取代当前分散的颜色值，确保全应用视觉一致性
- **FR-004**: 所有交互元素 MUST 有清晰的 hover、focus、active 和 disabled 视觉状态
- **FR-005**: 应用 MUST 使用应用内模态对话框替代浏览器原生 `confirm()` 和 `alert()`，确认对话框需显示影响数量
- **FR-006**: 导入队列 MUST 为每种文件状态（排队/上传中/已接受/重复/不支持/失败）提供图标和颜色区分
- **FR-007**: 筛选控件 MUST 以紧凑的下拉选择形式呈现，支持搜索过滤和滚动浏览选项
- **FR-008**: 标签输入 MUST 支持搜索已有标签的自动补全
- **FR-009**: 日期范围选择 MUST 提供可视化的日期选择交互
- **FR-010**: 批量操作 MUST 在选择资产后显示浮动工具栏，包含选择计数和可用操作
- **FR-011**: 删除确认 MUST 显示影响数量，需用户明确确认后才执行
- **FR-012**: 资产详情面板 MUST 在窄屏下以从侧边滑入的抽屉形式展示，可滑动关闭
- **FR-013**: 活跃筛选条件 MUST 以芯片形式显示，支持单个移除和全部清除
- **FR-014**: 空状态 MUST 提供有意义的视觉提示（图标 + 文字 + 建议操作）
- **FR-015**: 操作结果 MUST 以非阻断的通知形式反馈（成功/失败/部分成功），替代当前的行内反馈
- **FR-016**: 应用 MUST 支持 `prefers-reduced-motion` 媒体查询，在减少动画偏好下禁用所有过渡效果
- **FR-017**: 应用 MUST 保持与现有构建工具链的兼容性
- **FR-018**: 所有 UI 组件 MUST 满足 WCAG 2.1 AA 可访问性标准
- **FR-019**: 应用 MUST 移除已弃用的旧版前端代码

### Key Entities

- **主题令牌**: CSS 变量定义的颜色、圆角、间距、阴影值，用于统一应用视觉风格
- **组件状态映射**: 框架组件状态（default/hover/focus/active/disabled）到液体玻璃视觉表达的映射规则
- **交互模式**: 对话框、抽屉、下拉菜单、Toast 通知等交互模式的统一使用规范

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户在框架迁移后仍能识别液体玻璃视觉风格，核心面板的半透明、模糊和高光效果保持一致
- **SC-002**: 所有交互元素（按钮、输入框、复选框、下拉菜单）在 hover、focus 和 active 状态下都有明确的视觉反馈，覆盖率达到 100%
- **SC-003**: 导入流程中每种文件状态有独立的图标和颜色标识，用户无需阅读文字即可区分状态
- **SC-004**: 批量删除操作使用专业确认对话框而非浏览器原生弹窗
- **SC-005**: 前端包体积增长不超过当前基线的 50%（新增 UI 框架应按需引入，避免引入未使用的组件代码）
- **SC-006**: 应用在 3 个视口断点（>1050px、680-1050px、<680px）下都有可用且美观的布局
- **SC-007**: 键盘导航用户可以通过 Tab 键到达所有交互元素，焦点环清晰可见

## Assumptions

- 框架选择基于对玻璃态风格适配度、组件覆盖度、包体积、可访问性和定制自由度的综合评估，推荐方案详见规划阶段
- 迁移过程将保持后端 API 接口不变，仅重构前端渲染层
- 旧版前端代码将在迁移完成后移除
- 应用仍然作为单页应用由 Express 提供静态资源服务
- 暗色主题为主要主题，亮色主题作为可选的后续扩展（本次迁移不强制要求）
- 框架组件源码应直接归项目所有（复制模式），避免外部运行时 UI 库依赖锁定
